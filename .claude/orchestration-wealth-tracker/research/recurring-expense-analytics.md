# Research — Recurring Expense Analytics (Dépenses récurrentes & moyenne par catégorie)

Aspect of the MHTL Wealth PRD covered: §7.3 "Dépenses récurrentes" — detection, categorization, and average-spend-per-category computation for a 2-person French household.

## 1. Summary

Every consumer budgeting app that does this (Bankin', Linxo, Rocket Money, YNAB, Plaid-powered apps, Ntropy-powered apps) follows roughly the same three-stage pipeline:

1. **Ingest & normalize** raw transactions from an Open Banking aggregator (in France: Bridge, Powens/Budget Insight, or historically Budget Insight/Linxo's own aggregation).
2. **Categorize** each transaction (rule/merchant-name matching first, ML model as fallback or primary, always with manual user override) into a taxonomy of ~10-16 top-level categories with 60-130 subcategories.
3. **Detect recurrence** by clustering transactions per (household, counterparty/merchant, approximate amount) and checking whether the interval between occurrences is stable (weekly/monthly/quarterly/annual) within a tolerance window, then **compute averages** per category using a rolling window (typically 3/6/12 months) with either mean or median depending on how skewed/outlier-prone the category is.

For MHTL Wealth, the practical recommendation (detailed in §3) is: **don't build recurrence detection or categorization from scratch** — buy it. French aggregators Bridge and Powens both already return category codes and (Bridge specifically, and Powens via add-on products) recurring-transaction/subscription signals as part of the same DSP2 connection already required for account aggregation (PRD §8). Layer a thin manual-override + custom-category system on top, since automated categorization tops out around 85-99% depending on vendor and none of them is contractually guaranteed accurate for edge cases like CAF/CPAM government transfer labels.

## 2. Key Findings

### 2.1 How recurring-transaction detection works in the industry

- **Core signal set**: counterparty/merchant name (fuzzy-matched, not exact string match, because labels vary transaction to transaction — extra reference numbers, slightly different formatting), transaction amount (allowed to vary, not required to be identical), and the time interval between occurrences (checked against expected periodicities: weekly, monthly, quarterly, annual). This is consistent across vendors: fintech patents and product docs (Plaid, Ntropy, Subaio) describe the same three-signal model. [Expense Atlas — Plaid Recurring Transactions](https://www.expenseatlas.com/education/plaid-recurring-transactions/), [Subaio — How does Subaio detect recurring payments](https://subaio.com/subaio-explained/how-does-subaio-detect-recurring-payments)
- **Fuzzy tolerance windows**: amount tolerance is commonly ~5% (to absorb small price changes, FX drift, tips) and date tolerance is commonly ±3 days (to absorb weekends/bank-holiday shifts, "30 vs 31 day months", direct-debit processing lag). [USPTO patent 8380590 — recurring income detection](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8380590)
- **Plaid's `/transactions/recurring/get`**: production API returns "streams" (`stream_id`) of recurring inflow/outflow transactions, each carrying category, merchant, last amount, frequency, and a status field. Notably it supports **"early detection"** — flagging a stream as recurring before it has matured to 3+ occurrences, useful for a new subscription the user just signed up for. Plaid recommends at least 180 days of transaction history for good detection quality, and syncs transactions 1-4x/day depending on the institution. This confirms that 3 occurrences is roughly the industry-standard minimum to call something "confirmed recurring," with a lower-confidence "early" status before that. [Plaid — Recurring Transactions](https://plaid.com/blog/recurring-transactions/), [Plaid API docs](https://plaid.com/docs/api/products/transactions/)
- **Ntropy's approach** (a transaction-enrichment API vendor) explicitly does NOT rely on a naive clustering step; it computes pairwise transaction-to-transaction "distance" (combining merchant similarity + amount similarity + date-interval fit) and groups transactions into a **recurrence group** sharing the same counterparty (not necessarily the same amount). Their model explicitly tolerates **gaps** — e.g. a monthly subscription that was skipped for one month is still recognized as the same recurring series rather than being split into two series or discarded. This "gap tolerance" is an important design detail: naive "did payment N+1 arrive within the window" logic breaks the series entirely on a single missed month. [Ntropy — Quickly finding recurring events in massive sequences](https://medium.com/ntropy-network/quickly-finding-recurring-events-in-massive-sequences-9918cc57777c), [Ntropy — Recurrence docs](https://docs.ntropy.com/enrichment/recurrence)
- **ML vs. rules**: detection algorithms combine rule-based fuzzy matching with supervised/unsupervised ML for the harder cases (variable-amount subscriptions, irregular but genuinely recurring bills like variable-rate utilities). Patents describe "categorization, classification, pattern identification, NLP, semantic analysis, and value comparison" layered together. [USPTO — fraudulent bill/invoice payment detection](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10083452)
- **Rocket Money**: consumer-facing product built on Plaid; detects subscriptions/bills by scanning linked-account transaction history, flags free-trial-to-paid conversions, forgotten annual charges, price increases, and duplicate services. It explicitly has known blind spots: it can miss a subscription if the paying account isn't linked, or during initial-link processing delays. Good real-world confirmation that recurring-detection quality is bounded by aggregation completeness, not just algorithm quality. [Rocket Money — Missing subscriptions](https://help.rocketmoney.com/en/articles/934383-missing-subscriptions)
- **YNAB** takes a lighter-weight, more manual approach: users (or an "Auto-Assign" learning feature) set up **Scheduled Transactions** for known recurring items rather than the app purely inferring them from raw feeds; this is a hybrid where the system suggests based on past patterns but the user confirms/schedules explicitly. [YNAB — Scheduled Transactions](https://support.ynab.com/en_us/scheduled-transactions-a-guide-BygrAIFA9)

### 2.2 Categorization approaches

- **Do French aggregators provide categorization out of the box? Yes.**
  - **Bridge (bridgeapi.io)**: markets itself as categorizing "99%+ of transactions" into **16 main categories and up to 126 subcategories**, using a combination of algorithms (their marketing describes "three types of key algorithms" — implying rules + ML layered together) rather than a single classifier. This comes bundled with the same DSP2 aggregation connection already needed for account balances, so no separate integration cost. [Bridge — bank reconciliation/categorization](https://www.bridgeapi.io/bridge-et-vous/logiciels-de-comptabilite-et-gestion/comptabilite-rapprochement-bancaire) (site blocked direct fetch by robots/WAF at research time — verify current numbers directly against `docs.bridgeapi.io/docs/transactions-categories` during Discovery/build, as the WAF returned 403 to automated fetches).
  - **Powens (formerly Budget Insight)**: transaction objects returned by the Bank Transactions API include an array of `category` objects each with a `code` and `parent_code` (i.e., a 2-level taxonomy, category + parent category), returned as part of the standard aggregation response. Powens also sells a separate add-on "Categorizer" product for higher-fidelity ML categorization beyond the default codes. [Powens API — Bank Transactions](https://docs.powens.com/api-reference/products/data-aggregation/bank-transactions)
  - **Linxo**: markets ~85% categorization accuracy, and specifically claims its engine is trained on French transaction labels (handles quirks like CAF/CPAM benefit-transfer wording that US-trained models mishandle) — a relevant point for a French household. [FranceTransactions — Linxo](https://www.francetransactions.com/applications-gestion-budget-finances/linxo.html)
  - **Bankin'**: uses ML to auto-classify transactions into predefined categories (alimentation, transport, loyer/logement, loisirs, santé, etc.) and further rolls categories up into a higher-level "Essentiel / Plaisir / Épargne / Imprévu" (Needs/Wants/Savings/Unexpected) framing for its Budget feature — a useful secondary lens beyond raw category the app could optionally reuse. [Bankin support — Budget categories](https://support.bankin.com/hc/fr/articles/20540598544785-D%C3%A9finir-les-cat%C3%A9gories-du-Budget)
- **MCC codes are NOT a reliable universal source.** Merchant Category Codes (ISO 18245) are card-network-level codes, but Open Banking/DSP2 standards do not require banks to expose the MCC field in their transaction feed even when it's technically part of the spec — many French banks simply don't populate it. Aggregator payment/PSP-routing can also make the MCC reflect a payment processor rather than the true underlying merchant (e.g., a Stripe/Adyen umbrella code instead of the actual shop). **Conclusion: do not architect categorization around MCC availability; treat aggregator-provided category codes (Bridge/Powens) as the primary signal, MCC as a nice-to-have enrichment when present.** [Finextra — Open Banking Transaction Categorisation Mythbusting](https://www.finextra.com/blogposting/17809/open-banking-transaction-categorisation-mythbusting), [Merchant Category Code — Wikipedia](https://en.wikipedia.org/wiki/Merchant_category_code)
- **All vendors expect manual override.** Even at 85-99% claimed accuracy, every product (Bankin', Bridge-based apps, YNAB, Rocket Money) exposes user-editable category assignment and "rules" (e.g. "always categorize transactions from merchant X as category Y"), because misclassification of ambiguous merchants (Amazon = shopping vs. groceries vs. subscriptions) is unavoidable with automated methods alone.

**Recommendation**: reuse Bridge's or Powens' native category taxonomy as the source of truth (since the app is already paying for/using one of these aggregators per PRD §7.1/§8) rather than inventing a parallel taxonomy, and map their ~16 top-level / 60-126 sub-level codes down to a smaller "MHTL taxonomy" of ~10-12 top-level categories for the UI (average-per-category dashboard should not show 100+ rows). Allow user-defined custom subcategories on top, since Bridge/Powens Plus-tier apps like Bankin' gate custom categories behind paid tiers — MHTL Wealth is a private household app, so this restriction doesn't need to exist.

### 2.4 Calculation methodology used across products

- **Rolling windows**: 3/6/12-month rolling windows are the standard choice. YNAB's "Average Spent" metric explicitly computes a rolling average over **up to the last 12 months, excluding the current (in-progress) month**, starting from the first month with activity — this avoids the current partial month skewing the average low. [YNAB — Spending Breakdown](https://support.ynab.com/en_us/spending-breakdown-H1H7YxmD0)
- **Mean vs. median**: median is the statistically preferred measure of "typical" spend per category specifically because it's robust to outliers, whereas mean is dragged by rare large purchases (e.g. one €2,000 furniture purchase in "Shopping" for a month otherwise averaging €150). Standard stats guidance: use median when the category's spend distribution is skewed / has occasional large outliers; mean is fine for tightly-distributed recurring categories (rent, subscriptions) where variance is low. [SmartAsset — Median vs Average](https://smartasset.com/personal-finance/median-vs-average-income), [DataCamp — Mean vs Median](https://www.datacamp.com/tutorial/mean-vs-median)
  - **Recommendation for MHTL**: compute **both** per category — median as the headline "typical monthly spend" figure (resilient to one-off big purchases), and mean shown as a secondary figure or used for total-budget-forecasting math. For genuinely recurring, low-variance categories (housing, subscriptions, insurance-amortized) mean and median will converge anyway.
- **Amortizing irregular recurring expenses (annual insurance, etc.)**: the standard approach used across budgeting products is to convert an annual/quarterly recurring charge into its **monthly-equivalent** by dividing by the number of months in its cycle (e.g., a €480/year car insurance premium → shown as €40/month in the category average), so that "average monthly spend" isn't a giant spike in the one month it's charged and near-zero elsewhere. This requires the recurrence detector to carry a `frequency` field (monthly/quarterly/annual) per detected series, not just raw transaction dates. [Kudos — Budgeting for Subscriptions](https://www.joinkudos.com/blog/how-to-budget-for-recurring-subscription-expenses-in-2025)
- **Rolling forecast mechanics**: a rolling N-month window updates by dropping the oldest month and appending the newest each time a new month closes — standard technique, trivial to implement with a window-function query (`AVG()`/`PERCENTILE_CONT()` over a date-bounded partition) if using SQL. [Rolling 12-Month Budget](https://finhelp.io/glossary/how-to-build-a-rolling-12-month-budget/)

### 2.5 UX patterns for category averages, trends, and anomaly alerts

- **"This category is above your average" alerts** are the norm (Rocket Money, PocketGuard, Bankin', etc.) but best practice is to avoid being either too early (noise) or too late (guilt-trip after the fact). A commonly cited threshold pattern is graduated: e.g. 70% of typical = "heads up", 90% = "slow down", 100%+ = "over average, review". [ChatGiraffe — AI Alerts for Abnormal Spending](https://www.chatgiraffe.ai/article/red-flags-ai-alerts-for-abnormal-spending-over-budget), [MoneyPatrol — Budget Tracking Alerts](https://moneypatrol.com/moneytalk/budgeting/budget-tracking-software-set-alerts-before-you-overspend/)
- **Design principle**: keep the alert set small and high-trust — flooding users with per-transaction alerts causes users to tune out all of them. For a 2-person household account, this also implies alerts should be sent once per household event, not duplicated per user, and should probably surface in an in-app "This month" digest rather than push-notification-per-anomaly, unless the user explicitly opts into push alerts (this maps to PRD §7.3's "Alertes/tendances ... à valider en Discovery" open question — recommend validating notification cadence/threshold preferences in Discovery).
- **Visualization**: category-average dashboards typically pair (a) a bar/column chart of "this month vs. rolling average" per category and (b) a trend sparkline/line per category over the rolling window, consistent with YNAB's "Trends" report (bar graph with total/average/legend) and its "Income vs Expense" report. [YNAB — Spending Trends](https://support.ynab.com/en_us/spending-trends-H1inlhzAc)

### 2.6 Couple/shared-household considerations

- Products aimed at couples (Monarch, Honeydue, YNAB used jointly) converge on: each partner has their **own login** into the **same shared budget/dataset** (matches PRD §7.4's "deux profils utilisateurs liés à un même espace patrimonial partagé"), with category-average computations run once at the household level (not per-user), since the goal (PRD §10) is "the couple sees the same consolidated wealth/spend picture." Some couple-oriented apps add optional per-account privacy toggles (e.g. Honeydue) for accounts one partner doesn't want visible — out of scope per PRD §3 (single shared patrimoine, no partial privacy requested), but worth flagging as a Discovery question if requirements evolve. [Monarch — For Couples](https://www.monarch.com/for-couples), [Finny — Budgeting App for Couples](https://getfinny.app/blog/budgeting-app-for-couples)

## 3. Recommended Detection/Categorization Approach for MHTL Wealth

1. **Source of truth for categorization = the chosen aggregator (Bridge or Powens)**, not a custom ML model. Both return category codes on every transaction as part of the standard aggregation response at no extra integration cost beyond what PRD §7.1 already requires. Map aggregator categories → a smaller MHTL-specific taxonomy (~10-12 top-level categories, see table in §2.3) for a clean dashboard.
2. **Do not depend on MCC codes** being present — French banks inconsistently expose them via DSP2; treat as optional enrichment only.
3. **Recurrence detection**: implement (or, cheaper, use Bridge's own recurring/subscription detection if the app ends up on Bridge — verify current API surface at build time since docs were inaccessible to this research pass) a lightweight version of the "3-signal" model:
   - Group transactions by (household_id, normalized counterparty name, approximate amount within ~5-10% tolerance).
   - Within a group, check whether inter-transaction intervals cluster around a known periodicity (7±2 days weekly, 30±3 days monthly, ~90±5 days quarterly, ~365±10 days annual).
   - Require **3 occurrences** to confirm a series as "recurring" (industry norm per Plaid); optionally support an "early detection" / provisional status after 1-2 occurrences flagged for user confirmation, similar to Plaid.
   - Tolerate one missed occurrence (gap tolerance) before breaking a series, rather than resetting on the first miss (Ntropy's key design insight).
   - Always let the user manually mark/unmark a transaction group as recurring and manually correct category — this is universal across every product researched.
4. **Store a `frequency` (weekly/monthly/quarterly/annual) and `monthly_equivalent_amount`** on each detected recurring series so annual/quarterly charges (insurance, etc.) amortize cleanly into "average monthly spend per category" instead of spiking one month.

## 4. Calculation Methodology (recommended for MHTL)

- Compute, per category and per rolling window (offer 3M / 6M / 12M toggle in UI, default 6M or 12M):
  - **Median monthly spend** (headline figure — robust to outliers) computed over the household's aggregated (both users' transactions combined) monthly totals in that category.
  - **Mean monthly spend** (secondary figure, useful for total budget projections) — should also use the monthly-equivalent amortized value for annual/quarterly recurring items rather than raw transaction-date bucketing.
  - Exclude the current in-progress month from the rolling average (per YNAB's approach) so a half-elapsed month doesn't drag the average down; show current-month-to-date separately for comparison against the average.
- **Anomaly comparison**: `current_month_spend_in_category / rolling_median` → surface as a percentage delta ("+40% vs. your average"), with graduated thresholds (e.g. informational at +25%, warning at +50%) rather than a single hard trigger — exact thresholds to validate in Discovery per PRD §7.3.
- Compute at the **household level** (both users combined), since the couple shares one patrimoine per PRD §3/§7.4, not per-individual-user averages, unless Discovery later asks for a per-person breakdown as a secondary view.

## 5. Pitfalls (from research + product post-mortems)

1. **Internal transfers between the couple's own accounts must be excluded from expense totals.** This is the single most commonly cited bug pattern (Quicken, Actual Budget, Monarch support docs all address it explicitly): moving money checking→savings, or paying off a linked credit card from a linked checking account, is not spend — it must be tagged as a transfer, or the app will double-count expenses (once when the card is charged, again when the bill is paid). Aggregators usually flag inter-account transfers if both accounts are linked under the same user; the app must respect that flag category-wide and exclude "Virements internes" from all average-spend calculations by default. [Quicken — Transferring money between accounts](https://info.quicken.com/mac/transferring-money-between-accounts)
2. **Refunds/reversals should net against the original expense category, not appear as income.** Standard accounting practice (and consumer-app convention) is to apply a refund as a negative amount in the same category as the original purchase, reducing that category's net spend for the period — not recording it as new income, which would distort both the expense average and any income tracking. [Navan — What is a Negative Expense](https://navan.com/resources/glossary/what-is-negative-expense)
3. **Duplicate transactions from aggregator resync**, and **pending vs. posted transaction** mismatches: bank-sync integrations (per Monarch/Actual Budget bug trackers) commonly produce duplicates when re-syncing after a connection issue, or when a pending transaction later posts with a slightly different amount/date and isn't deduplicated against the pending record. Needs an idempotency key (aggregator's own transaction ID, not a derived hash of amount+date+label alone, since those can collide) and a reconciliation strategy that replaces pending transactions with their posted counterpart rather than appending a second row. [Monarch — Troubleshooting Duplicate Transactions](https://help.monarch.com/hc/en-us/articles/32110313427604-Troubleshooting-Duplicate-Transactions)
4. **Currency conversion for foreign transactions**: for a French household, occasional non-EUR transactions (travel, foreign online purchases) come through already converted to EUR by the card network/bank, but often bundled with an FX/foreign-transaction fee (~1-3%) that may show as a separate line item or be embedded in the charged amount depending on the bank. Category-average math should decide up front whether FX fees are folded into the merchant's category or bucketed separately under "Services/Frais bancaires" — recommend the latter for cleaner "average spend on X" figures (a foreign restaurant bill shouldn't be inflated by a bank's FX markup for restaurant-category averaging purposes). [Bankrate — Foreign transaction fees vs currency conversion fees](https://www.bankrate.com/personal-finance/foreign-transaction-fees-vs-currency-conversion-fees/)
5. **Annual/irregular recurring expenses skew monthly averages if not amortized** (see §4) — a €900 annual home-insurance payment landing in March will make "Logement" look like it spiked 5x that month if the average is computed on raw monthly totals rather than smoothed/amortized recurring amounts.
6. **Categorization accuracy ceiling**: even best-in-class French-trained engines (Linxo claims ~85%) or aggregator marketing claims (Bridge ~99%) are not 100% — always design for user correction as a first-class flow, and apply corrections as standing rules ("always categorize merchant X as category Y") so the same manual fix doesn't have to be repeated every month.
7. **Two-user household double-visibility, not double-counting**: both spouses seeing the same shared transaction feed is correct (PRD requirement), but the aggregation/averaging logic must operate on the deduplicated household-level transaction set, not sum "user A's view" + "user B's view" of the same joint account (which would double the numbers if the data model isn't careful about ownership of shared accounts vs. per-user data).
